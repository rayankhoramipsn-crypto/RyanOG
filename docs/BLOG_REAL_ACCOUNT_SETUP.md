# فراهم‌کردن امن حساب واقعی برای تست وبلاگ

این راهنما فقط برای staging با شناسهٔ `cxtytbjvdlngahytfilr` و نام **TRISO TEST** است. هیچ رمز، کلید خصوصی، JWT، refresh token یا فایل نشست را در چت، issue، PR یا مخزن قرار ندهید.

## ۱. دو حساب اختصاصی staging

مالک پروژه در [Authentication → Users](https://supabase.com/dashboard/project/cxtytbjvdlngahytfilr/auth/users) دو کاربر جدید با ایمیل‌های تحت کنترل خودش بسازد: یکی برای مدیر آزمایشی و دیگری برای کاربر عادی. از حساب شخصی، مدیر اصلی یا کاربر موجود استفاده نشود. رمزها مستقل و قوی باشند و فقط در مدیر رمز/Secrets نگهداری شوند.

از مسیر Add user / Create new user یا Auth Admin API رسمی استفاده شود. ساخت مستقیم ردیف در auth.users با SQL، حساب مناسب تست ورود نمی‌سازد. در صورت تأیید ایمیل توسط مالک برای این حساب‌های اختصاصی، تست ورود ممکن است اما تحویل ایمیل همچنان تست‌شده محسوب نمی‌شود. برای تست ایمیل باید جریان واقعی تأیید ایمیل جداگانه طی شود؛ تنظیم سراسری تأیید ایمیل را غیرفعال نکنید.

نقش مدیر باید توسط مالک از مسیر معتبر سمت‌سرور در app_metadata ثبت شود. برای نمونه، در محیط خصوصیِ مالک که کلاینت Admin از قبل به **همین staging** متصل است:

```js
// Execute only in the project owner's trusted server environment.
// admin is a Supabase Admin client; never create this client in browser code.
const { data, error } = await admin.auth.admin.createUser({
  email: testAdminEmail,
  password: testAdminPassword,
  email_confirm: true,
  app_metadata: { role: 'admin' },
})
if (error) throw new Error('Test admin creation failed')
// Do not log data: it contains a user record. Record only the new ID privately.
```

حساب دوم با همان روش و `app_metadata: { role: 'customer' }` ساخته شود. اگر دو حساب قبلاً از داشبورد ایجاد شده‌اند، فقط شناسهٔ همان حساب آزمایشی جدید را با `admin.auth.admin.updateUserById(testUserId, { app_metadata: { role: 'admin' } })` ارتقا دهید؛ شناسه و پروژه را پیش از اجرا بررسی کنید. متادیتای موجود را در صورت نیاز با مقدار قبلی ادغام کنید. user_metadata و localStorage/sessionStorage مسیر اعطای نقش نیستند. پس از تغییر نقش، ورود تازه انجام شود تا JWT تازه صادر شود.

کلید secret/service_role لازم برای عملیات مالک فقط در محیط خصوصی خود مالک باقی بماند؛ آن را به تست مرورگر یا این گفتگو تحویل ندهید. [مرجع ساخت کاربر](https://supabase.com/docs/reference/javascript/auth-admin-createuser) و [مرجع ویرایش app_metadata](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid).

## ۲. دسترسی شبکهٔ محدود و Secrets محیط تست

در تنظیمات محیط اجرای این کار، دسترسی HTTPS فقط به `cxtytbjvdlngahytfilr.supabase.co` برای API staging فراهم شود. پراکسی محیط نیز باید سالم باشد؛ در بررسی فعلی اتصال به خود پراکسی شکست خورد. قبل از استفاده از رمزها، دسترسی API بدون اطلاعات حساب بررسی شود. دسترسی به پروژهٔ production یا دامنهٔ wildcard لازم نیست. تغییر تنظیمات انتشار سایت، DNS یا تنظیمات Auth برای این کار لازم نیست.

اگر تست را همین عامل اجرا می‌کند، مالک در بخش مدیریت امن Secrets محیط اجرا چهار مقدار زیر را ثبت و فقط به این محیط آزمایشی متصل کند:

- `TRISO_TEST_ADMIN_EMAIL`
- `TRISO_TEST_ADMIN_PASSWORD`
- `TRISO_TEST_USER_EMAIL`
- `TRISO_TEST_USER_PASSWORD`

URL ثابت staging و کلید publishable عمومی کافی‌اند؛ secret/service_role نباید به این چهار مقدار اضافه شود. رمزها در پیام، دستور شل، فایل ردیابی‌شده، خروجی لاگ یا متغیرهای عمومی frontend مانند NEXT_PUBLIC_* قرار نگیرند. در صورت نبود امکان ثبت Secrets، مالک تست را روی دستگاه خودش با مدیر رمز/ورودی مخفی انجام دهد؛ رمز را برای انتقال از چت استفاده نکند.

عامل باید وجود و آماده‌بودن bindingهای Secrets را از وضعیت محیط بررسی کند و فقط SDK/runner را با مقادیر تزریق‌شده اجرا کند؛ مقدارها چاپ یا برای کشف محتوا خوانده نشوند. در این نوبت وضعیت محیط هیچ secret، runtime credential یا outbound identity ثبت‌شده‌ای گزارش نکرده است. وجود چند کاربر در جدول Auth به معنی دسترسی به حساب آزمایشی نیست؛ رمز یا نشست کاربران موجود استخراج نمی‌شود.

## ۳. اجرای واقعی؛ بدون پاسخ fixture

همان نسخهٔ `fix/site-blog` به‌صورت محلی سرو شود؛ سایت منتشر نشود. سه browser context مستقل برای مهمان، کاربر عادی و مدیر بسازید. در دو context کاربری، فرم واقعی ورود Account فروشگاه استفاده شود و سپس در همان tab به وبلاگ بروید؛ نشست برنامه در sessionStorage همان tab است. تست موجود `tests/browser/blog.cjs` پاسخ API را جعل می‌کند و برای این مرحله مناسب نیست.

ثبت trace/HAR، ویدئو و dump شبکهٔ احراز هویت خاموش باشد. گزارش فقط نام بررسی، نتیجه و وضعیت HTTP را نگه دارد؛ request headers، payload ورود، پاسخ Auth و محتوای sessionStorage ثبت نشود.

1. مدیر یک مقاله با نامک تصادفی مختص این اجرا بسازد، شناسهٔ برگشتی را نگه دارد، دوباره ذخیره کند و ثابت کند همان شناسه ویرایش شده است.
2. متن، تصویر HTTPS و زبان‌های EN/FA/AR با دادهٔ خود تست بررسی شوند. متن HTMLمانند باید متن بماند؛ منبع تصویر انتخابی نباید اطلاعات حساس داشته باشد.
3. همان مقاله از پیش‌نویس به منتشرشده با زمان گذشته و سپس بایگانی‌شده تغییر کند. یک مقالهٔ زمان‌بندی‌شدهٔ آینده نیز فقط از دادهٔ خود تست ساخته شود.
4. context مهمان و کاربر عادی با درخواست واقعی فقط رکورد منتشرشدهٔ موعدرسیده را ببینند. خواندن با شناسهٔ دقیق پیش‌نویس، بایگانی و آینده باید خالی/رد شود.
5. کاربر عادی با JWT خودش نتواند مقاله بسازد، ویرایش یا حذف کند. برای UPDATE/DELETE، پاسخ 200 با آرایهٔ خالی نیز می‌تواند رد توسط RLS باشد؛ مدیر باید جداگانه ثابت کند رکورد تست تغییر نکرده است. مهمان باید جدا آزمایش شود.
6. JWT و refresh token واقعاً از Auth دریافت شوند. هنگام بازبودن ویرایشگر، انقضای واقعی توکن انتظار کشیده شود. برای بررسی سریع‌تر مسیر refresh می‌توان ساعت Date مرورگر تست را با Playwright جلو برد، یا قبل از بارگذاری وبلاگ expires_at نشست آزمایشی را به گذشته برد تا برنامه refresh واقعی بزند. دستکاری expires_at بعد از بازشدن صفحه به‌تنهایی کافی نیست، چون صفحه نشست را در حافظه نگه می‌دارد. این روش‌های سریع، مسیر refresh واقعی را تست می‌کنند ولی انقضای رمزنگاری‌شدهٔ JWT را ثابت نمی‌کنند. تغییر تنظیم سراسری JWT لازم نیست.
7. با نشست تمدیدشده، یک ویرایش واقعی دیگر ذخیره و با خواندن مجدد تأیید شود. هیچ نقش مدیریتی با کلید service_role شبیه‌سازی نشود.

پس از تست، مدیر فقط شناسه‌های مقاله‌های ساخته‌شده توسط همین اجرا را حذف کند. نشست دو کاربر آزمایشی از مسیر Auth sign-out لغو شود؛ مالک فقط همان دو حساب جدید را با شناسهٔ خصوصی ثبت‌شده حذف و Secrets محیط را پاک کند. حذف حساب به‌تنهایی access token صادرشده را فوراً باطل نمی‌کند. محتوای دیگر و حساب‌های قبلی دست‌نخورده بمانند.

## وضعیت فعلی

این راهنما و مسیر بالا آماده‌اند؛ حساب‌ها در این نوبت ساخته نشده‌اند و هیچ تست واقعی ورود، تمدید نشست یا مدیریت مقاله با حساب کاربری اجرا نشده است. آماده‌شدن شبکه و Secrets باید دوباره تأیید شود؛ صرف افزودن این راهنما به PR، موفقیت تست محسوب نمی‌شود.
